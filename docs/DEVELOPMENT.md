# Разработка и проверки

## Подготовка

Нужен Bun версии из `package.json` или новее. Для полного окружения на Linux
выполните `nix develop path:.` или `nix-shell` из корня проекта. Обе команды используют
закреплённый `flake.lock` и общий список пакетов в `nix/dev-shell.nix`.
Nix-файлы форматируются через `nix fmt`; остальные файлы — через Prettier.

```sh
bun install --frozen-lockfile
bun run lint
bun run typecheck
bun test
```

Сетевые учётные данные и Ollama не требуются для тестов. Интеграционный тест
аудиопотока использует настоящий FFmpeg, если он установлен; иначе пропускается.
Остальные проверки процессов используют дочерние процессы Bun. Терминальные тесты
работают через псевдотерминал: проверяют навигацию клавишами и мышью, разделённые пакеты событий, закрепление позиции
при новых логах, ограничение истории, resize, буквальный поиск с подсветкой и
выход через `q` или Ctrl+C.

Некоторые песочницы блокируют запись в каналы дочерних процессов. Ошибки EPERM
при проверке потоков нужно проверять в среде, разрешающей subprocess I/O, а не
скрывать пропуском тестов. Живое подключение к Discord, Telegram, Ollama и реальное
извлечение музыки с провайдеров остаются отдельной интеграционной проверкой.

Сборка предварительно включает Opus-кодировщик и его WASM через
`scripts/audio-build.ts`: динамический загрузчик prism-media иначе обращается
к `node_modules` исходного проекта. Нативный DAVE обрабатывается на последнем
этапе компиляции. Тест `standalone-audio` собирает бинарник и проверяет DAVE
и кодирование PCM в Opus с закрытым checkout через Bubblewrap; без `bwrap`
эта проверка пропускается. Готовый бинарник можно проверить без сети командой
`./dist/relaksacher check-audio`.

## Структура проекта

```text
index.ts                       запуск бота, TUI и команды полного рестарта
src/
  config.ts                    конфигурация окружения
  types.ts                     общие публичные контракты
  core/
    assistant/                 сессии модели, контекст, промпты и фоновые решения
    memory/                    постоянная память и история расшифровок
    music/                     очередь воспроизведения и локальный мониторинг
    speech/                    подготовка текста, транскрипция и Whisper
    tools/                     инструменты модели, поиск и погода
    *.ts                       общие очереди, серии сообщений, пути и shutdown
  adapters/
    discord/
      access/                  настройки доступа и приватное меню
      music/                   команды, кнопки и голосовой плеер Discord
      *.ts                     клиент, сообщения, потоковая доставка и TTS
    telegram/                  клиент, Bot API, форматирование и сообщения
    terminal/                  CLI, TUI, навигация, мышь и поиск
    music/                     музыкальные источники, метаданные и плейлисты
    speech/                    адаптер Silero и загрузка аудио
    shared/                    общая работа с изображениями
scripts/                       проверка размера файлов и Python CLI Silero
test/                         тесты по соответствующим подсистемам
```

`src/runtime/` содержит заменяемую сборку приложения, загрузчик и постоянные
соединения мессенджеров. Для проверки изменений логики без обрыва генерации
используйте `bun start`, затем кнопку `[R Рестарт]` или клавишу `R` в TUI.
`bun dev` использует `--watch` и перезапускает процесс с отменой текущей работы.

В `test/` используются группы `assistant/`, `discord/`, `telegram/`, `terminal/`,
`music/`, `speech/`, `tools/` и `core/`. Общие фабрики и временные каталоги находятся
в `test/support/`. Например, `bun test test/discord` запускает проверки Discord,
а `bun test test/music` — проверки музыкальной подсистемы.

Входные файлы подсистем называются `index.ts` и содержат реальные фабрики,
а не дополнительные цепочки реэкспортов. Discord-специфичные меню и состояния
хранятся в `adapters/discord/music/`; получение треков, метаданных и переносимые
плейлисты — в `adapters/music/`. Ядро не зависит от платформенных клиентов.
При переносах обновляйте также динамические импорты, `Bun.resolveSync`, пути
к ресурсам от `import.meta.url` и описание модулей в архитектуре.

## Размер модулей

Каждый TypeScript-файл в `src/`, `test/`, `scripts/` и `index.ts` ограничен
600 физическими строками, включая комментарии и пустые строки. Предпочтительный
размер самостоятельного модуля — 200–400 строк. Делите код по ответственности:
состояние, доставка, команды и интерактивные элементы; общие тестовые фабрики
держите отдельно от самих проверок. Сжатие форматирования не заменяет разделение.

`bun run check:size` проверяет размер и завершает работу с ошибкой при превышении.
Эта проверка автоматически выполняется перед линтером в `bun run lint` и
`bun run lint:fix`, включая новые, ещё не добавленные в Git файлы.

## Линтер

```sh
bun run lint
bun run lint:fix
```

Oxlint проверяет `index.ts`, все исходники `src/`, тесты `test/` и TypeScript-инструменты `scripts/`. Конфигурация
`.oxlintrc.json` включает проверки корректности JavaScript/TypeScript и плагины
TypeScript, Unicorn и Oxc. `Bun` объявлен глобальным объектом. Зависимости,
локальная память и служебные каталоги исключены.

Любая ошибка или предупреждение завершает проверку с ненулевым кодом. `lint:fix`
применяет доступные безопасные исправления, после чего нужно проверить diff и
запустить форматирование. Prettier отвечает за стиль, а TypeScript — за проверку
типов и неиспользуемых локальных переменных/параметров; линтер дополняет обе проверки. Неиспользуемые локальные исключения правил
тоже проверяются. Намеренно неиспользуемые параметры и переменные обозначаются
префиксом `_`; исключение для фильтра управляющих символов терминала локально
и снабжено причиной.

## Форматирование

```sh
bun run format
bun run format:check
```

Prettier установлен локальной dev-зависимостью. Стиль задан `.prettierrc.json`.
Команда форматирует исходники, тесты, JSON-конфигурацию и Markdown. Исключения в
`.prettierignore`: зависимости, служебные каталоги, память, секреты, локальные
факты/личность и lockfile, который обновляет сам Bun.

При добавлении зависимостей коммитьте `bun.lock`. Для изменения форматирования
обновляйте общую конфигурацию, а не исключения для отдельных функций.

## Документирование изменений

Добавляйте описание модуля и JSDoc для его публичных функций и контрактов.
Описывайте назначение, ограничения, отмену и значимые побочные эффекты. Для сложных
внутренних переходов объясняйте инварианты. При изменении пользовательских команд
обновляйте [справочник](COMMANDS.md); при изменении архитектуры —
[описание модулей](ARCHITECTURE.md). Настройки запуска описаны в [README](../README.md).

После изменения `bun.lock` выполните `bun scripts/nix-lock.ts` и включите
`nix/package-lock.json` в изменение. Это представление Bun lock для offline
установки через `importNpmLock`; `bun.lock` остаётся основным lockfile.
Проверка пакета: `nix build path:.`.

## Компилятор и предупреждения AOT

`bun run build` использует стабильный Bun 1.4.4 из `nix/bun-compiler.nix`;
системный Bun не заменяется. Архивы x64 и ARM64 закреплены по постоянным URL
релиза и SHA-256. Перезаписываемый canary-релиз не используется: его старые
GitHub assets удаляются и ломают чистую установку в CI. Flake-пакет `bun-compiler`
также доступен под прежним именем `bun-canary` для совместимости команд.

Обычная сборка создаёт самостоятельный исполняемый файл с JIT. Для зависимостей
этого проекта это сохраняет динамические загрузчики модулей и регулярные выражения
без ограничений экспериментального AOT. `./build.sh --aot` оставлен для экспериментов;
предупреждения в этом режиме не подавляются:

- `TS100064`: динамические загрузчики Discord Voice, Prism и DAVE. AOT требует,
  чтобы выбранный модуль был встроен заранее. OpusScript и его WASM включает
  `scripts/audio-build.ts`, установленные нативные библиотеки DAVE встроены как assets.
  Произвольные дополнительные модули с диска AOT-сборка не поддерживает.
- `TS100150` / `TS100151`: необязательные альтернативы библиотек: локальные/WASI
  варианты DAVE, `zlib-sync`, `supports-color`. Зависимости перехватывают отсутствие
  этих модулей; устанавливать все альтернативы ради устранения диагностики не нужно.
- `TS100058`: регулярные выражения в Markdown, CSS-селекторах, Discord и поиске TUI
  выполняются интерпретатором AOT. Это ограничение оптимизации компилятора, не ошибка
  выражения. Обычная JIT-сборка не имеет этого ограничения.

После обновления компилятора проверьте полный набор `bun test`, lint, typecheck,
форматирование, сборку и запуск standalone-файла. Не убирайте флаги или выражения
регулярных выражений ради обхода диагностики: это может менять Unicode-поиск.

### Сравнение JIT и AOT (2026-11-01)

Проверено на Intel Core Ultra 9 275HX, Linux x64, одним компилятором
1.4.4-canary.1+3f3a9ff87. Воркеры закреплены за CPU 2, порядок трёх запусков
каждого режима чередуется. Для каждого сценария: 500 мс прогрева, затем медиана
трёх замеров по 750 мс; таблица показывает медиану результатов трёх процессов.
Выходные данные сценариев в обоих режимах совпали. Повторение:

```sh
BENCH_CPU=2 nix shell path:.#bun-canary --command bun scripts/benchmark-runtime.ts
```

Скрипт компилирует оба режима, использует настоящие функции проекта и Cheerio,
не подключается к чатам или сети. Сырые результаты —
`/tmp/relaksacher-runtime-benchmark/results.json`. `BENCH_CPU` задаёт Linux CPU
для `taskset`; без него закрепление отключено.

Пропускная способность, операций в секунду; больше — лучше:

| Сценарий          |     JIT |     AOT |
| ----------------- | ------: | ------: |
| `telegram_format` |   3,621 |   4,491 |
| `model_context`   | 132,580 | 115,517 |
| `tui_search`      |  33,772 |  35,217 |
| `web_extract`     |   3,173 |   1,944 |

Медиана пикового RSS воркера: JIT 101,3 MiB, AOT 99,3 MiB. Отдельно измерены
20 запусков полного бинарника каждого режима до ожидаемой ошибки отсутствующего
файла фактов: JIT 133 мс и 73,5 MiB RSS, AOT 28 мс и 58,0 MiB. Это проверка
раннего старта и импорта модулей, а не времени подключения к Discord/Telegram.

AOT быстрее форматирует этот Markdown и немного быстрее ищет текст; JIT быстрее
собирает контекст и разбирает HTML. Для постоянно работающего бота выбран JIT:
нет ограничений AOT на загрузчики зависимостей, выше пропускная способность
веб-обработки, а разница памяти под нагрузкой мала. Это не измерение полной
задержки ответа: Ollama, внешняя сеть, FFmpeg и Whisper работают отдельно,
и их скорость от режима JavaScript не меняется. Результаты зависят от CPU и данных.
